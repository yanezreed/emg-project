# Project testing

## Covered

This document explains how the individual components of my application were tested throughout development of this project. 

It covers the many edge cases I was able to consider within testing, the identified standout bugs that were discovered in runtime, and how solutions were found to address these issues as the size of the project grew.

Given the very nature of this project, which handles highly sensitive data such as customer data retrieved through ebays api, and access token data acquired through the oauth authentication process. Testing was never something that could be postponed to the latter stages of development, and was therefore carried out manually throughout the entire process.

## Manual vs automated testing

While automated unit testing frameworks such as `pytest` do exist and are something I have experience with through my work within harvards cs50 course. Because of the incremental nature of this projects development, the components within required constant testing as they were built and integrated, rather than at a single fixed point. 

This was simply because any issues introduced within any one of the three layers of my project, had the potential to affect functionality across the entire codebase. Plus the actual order in which components were developed and tested, did not correspond at all to what architectural layer they resided in. This is because many of the components depended on the functionality from other layers to make testing possible at all. 

So for the sake of clarity of this document, I have organised the testing of these components into their corresponding architectural layers, as can be seen below.

## API Layer

### Ebay endpoints

Throughout the integration of ebay’s api oauth process into my project, each ebay endpoint involved had to be tested manually, achieved through calling the relevant function it corresponded to it and inspecting the http response it produced. Or an absence of one in many cases.

The method `get_conversations` is a clear example of this, as it was tested by simply running the function and verifying the list of conversation objects it returned. One obstacle involved with its implementation was the initial absence of `conversation_type = from_members`. As without this parameter, the lists received initially through testing, included a large number of automated conversations generated by ebay itself. Its inclusion however, meant that only conversations received by my application were those between the user’s ebay account and their customers.

The `get_conversation_messages` method was also tested by passing a set `conversation_id` to this method, to verify that it was the full and correct message thread returned. Ensuring the existence of each message object within the thread, to confirm the presence of the expected field names in `sender_username` and `message_body`.

Field names were also a tricky aspect of building these functions. As until a successful oauth flow could be completed, and a correctly formatted http request produced a valid response, the exact field names returned by ebay’s api were unknown to me. By gaining access to the initial json responses to my flask server, allowed fields such as `senderUsername` and `messageBody` to be identified.

Lastly, I was able to test my `send_message` method by creating a reply to a real conversation between two of my accounts within ebay's live system. By logging into my own account within eBay's messaging platform directly, I was able to see for myself if the message had correctly appeared. The http response from ebay was also monitored throughout, with `200` or `201` status code confirming a successful execution.

### Error handling

To test the various runtime errors assigned to the http requests within `ebay_client.py` invalid values were purposely supplied to each of them. Made up, invalid conversation ids were used to confirm that an unexpected ebay status code received through the response, would cause the appropriate exception to be raised.

The accompanying error message was also checked within the ui, making sure it accurately identified which of the requests had failed.

### Oauth flow

The oauth flow was tested extensively throughout its integration into my project, and this was because of the sheer amount of complexity that came along with it.

#### Local host rejection

My first major finding during testing was that ebay would only accept a callback url pointing to a publicly available url. This was discovered early on in the project as it was originally planned that a local host would be used to receive the authorisation code passed by ebay’s api. 

This discovery was made during testing, as once the ebay login page had been completed, the browser would simply display an error rather than being redirected to the callback url I had submitted to ebay. The local flask server would also show no incoming requests within its console, indicating to me that ebay had refused the redirect rather than the request itself failing. At this point it was understood that a publicly accessible url was required.

#### Render wind up delay

During the testing of this newly implemented render hosted server, it became apparent that the free tier server hosting came with the trade off of an initial windup period, activated whenever the server had been inactive for over fifteen minutes. Meaning that the server must restart before processing any incoming requests. This would cause the initial request to my flask hosted server, made to the `/start` route, to take noticeably longer to complete while the render server started. Once the server had restarted, the original request continued, with the `/start` route redirecting the browser to ebays login page.

This issue was confirmed to me through the render dashboard, as the server would show that it was “in the process of restarting”. The restart process could also be recognised through a loading page displayed at the `/start` url within the browser. Confirming that the delay was caused by the current tier of render service starting from an inactive state.

Initially this seemed like a significant problem, and that an alternative solution to the cloud application platform might need to be incorporated. As a failed first request, due to a restarting server, would leave my application with no way to progress the oauth flow.

However, after understanding the wind up process and why it occurred, a polling mechanism was introduced within `oauth_start.py`. 

My initial single request design was substituted, as due to the varying restart times of the render server, it could not be guaranteed that the request made to `/check_token` would not immediately fail or find the complete token data on first attempt.

In the place of this single check approach, the `request_server` method was designed. Using a `qtimer` to continually request the `/check_token` route for thirty attempts, any unsuccessful attempts would not be treated as a final failure. The process would instead only complete successfully if a `200` response containing valid token data was received. And if the maximum number of attempts was instead reached without receiving valid token data. The current `qtimer` initiating the requests, would be stopped, and a warning message is displayed to the user. The current authorisation attempt being abandoned.

#### Token storage

The oauth 2.0 flow, and access token management in particular, was not something I had prior experience with before this project. And required a lot of research before designing my own integrated version within my project, to allow the transmission of customer conversations within my application.

This research included a range of video resources covering oauth 2.0 implementation in python, as well as reviewing ebay’s own api documentation. This allowed me to build up understanding, to later implement this flow gradually, step by step. Rather than implementing the entire token system in one go. Each component was built, and tested, following the natural order of how tokens move through the render hosted server and the application. Below are how each of these functions were tested:

The `save_tokens` function was the first to be built and tested. As none of my other token management methods would be able to function without a way to store the actual access token data, both within my render hosted server and the desktop application. This method was tested by ensuring that the complete token response was within the servers `ebay_tokens.json` file after a successful oauth exchange. Confirming that the token data had been written correctly. This was verified first through my render servers dashboard, and then locally within my desktop application once my polling function had been implemented through `request_server`. Note, the values received by my desktop applications file included the expected `access_token`, `expires_in` and `received_at` keys. As the entirety of the token data is not transferred.

Next `load_tokens` was built and tested straightforwardly, by ensuring that what was returned by the function was a python dictionary and not the original json. One edge case covered during testing here was the scenario where this method attempted to load the `ebay_tokens.json` file before the file existed. Which would be the case on the initial first use of this application within a new local desktop environment. Now, this function will result in a `none` value being returned, rather than an error being raised.

The current `token_expired_check` method was also tested by manually altering the `received_at` value within the local temporary `ebay_tokens.json` file. With the timestamp of the data, portraying that it was received far in the past, now representing an expired access token. This allowed me to verify that `token_expired_check` would test the token data correctly with a `true` returned value. Note, this method was also tested with valid token data to ensure that a `false` value was returned.  

It was also at this stage of testing that the potential issue of access tokens expiring mid workflow was identified, between the time of the token being checked by my workflow and actually being used within a request.

As a solution, a thirty second buffer was implemented, and subtracted from the calculated expiry time, reducing the lifetime of the token within my application. This ensured that tokens checked near the end of their lifespan would be recognised by my application as already expired.

This buffer was tested again by altering a valid access tokens `received_at` value, and confirming that near the end of its lifespan it would be treated as already expired, using the `token_expired_check` method, despite having a small amount of its lifespan remaining.

Lastly, all of the http post and get requests made through the oauth flow, were all tested individually by their corresponding expected results to the responses they actually received.

As all of the requests made to ebays api required specific parameters and field names, defined by ebay themselves, a successful response was the only way to confirm that each request had been implemented correctly initially. As unfortunately the documentation at this point was quite unclear, so this stage included alot of trial and error. In addition to a lot of online research.

## Application layer

### User authentication

Account creation was tested by manually attempting to create multiple user accounts within my application, using the same username. In the effort to verify that my sqlite `unique` constraint would correctly cause an `integrityerror` to be raised. 

This returned an error from sqlite, was then caught by my `create_user` method, resulting in a failed result. Confirming that the username already exists within the database.

In a similar way, password verification was also tested by attempting to log into my application using both incorrect and correct passwords for existing accounts. Allowing me to confirm that my `verify_password` method would return `true` for a correct password, and `false` an incorrect one.

Separately, two accounts were also created with identical passwords. This was done in an attempt to confirm if my `pbkdf2-hmac-sha256` implementation would produce two distinct hexadecimal values within the database.

This is because the `hash_password` produced generates a unique salt for each password, before it is passed to the `pbkdf2` key stretching function.

### Data sanitisation

The accuracy of personally identifiable information detection within the `sanitise_text` method was checked through the testing of a range of text samples containing various different types of sensitive information. These samples were passed through `sanitise_text` to assess the accuracy of microsofts presidio libraries redaction. With the output of this method checked through the ui of my application, to confirm if the expected information had been removed.

Edge cases were also used in addition to the various types of data already tested, such as telephone numbers and email addresses. These included location addresses embedded within long sentences and payment information written in non standard formats, in an effort to access presidio ability to catch these vague cases. It should be noted that some edge cases were found to pass through this sanitisation step, which is why the mandatory user review of the results was implemented.

### Ui sanitisation enforcement within workflow one

The “generate reply” button was also tested in `generate_dialog.py` to verify that the button itself remained disabled, until the sanitisation process had completed. To stop the user from accidentally processing unsanitised customer conversations within the local ai model.

It was also tested that, in the case of the user cancelling the review, that this button would also stay disabled. Confirming that the application user, in no way could bypass the need to successfully sanitise the information fed into the ai, as well as the mandatory review.

### Ai generation

The prompt building aspect of my reply generation process was first manually tested by running `build_prompt` and inspecting the results. Verifying that the sanitised conversational history, the business information within `business_info.txt` and any other additional user instructions were all included.

During this testing, one major bug that was identified within `build_prompt` was that the original implementation of `return f.read()` caused the function to exit after reading `business_info.txt`. Because of this, the ai model never actually received either the conversational history, or the user instructions within the prompt. Resulting in the production of completely useless outputs. This was fixed by replacing `return f.read()` with `business_info = f.read()` allowing the remainder of `build_prompt` to execute correctly.

In addition, the locally running ollama instance, using the llama 3.1 8b model, was also tested to verify that the `call_local_ai` method received a valid response after executing the local http request. And that the generated reply produced by the model, could then be successfully returned to the application.

The timeout behaviour of my application was also tested by killing the llama instance before the request was sent. In an effort to confirm that the application handled the failure correctly, rather than becoming unresponsive. This was verified by ensuring that the request timed out correctly, and the exception was caught, and an error message was displayed to the user. Allowing the application to continue running.

### Ai generation

#### Workflow one prompt

Prompt building for both workflows was also heavily tested. Done by calling each of the methods for both workflows, and manually inspecting the results.

Within workflow one, the way the prompt is constructed within `reply_dialog.py` is first through the `build_prompt` method, so this was one of the initial elements of this file to be manually tested. Ensuring that the instructions from `prompt_workflow_one.py` were correctly gathered, by printing the prompt to the terminal. This also confirmed that the internal information from `business_info.txt` was also correctly read and combined with the rest of the prompt.

After this, the sanitised conversation was also tested, to see if each message within had been correctly labelled either `customer` or `seller` dependent on the `sender_username` value within each of the message objects, and if it matched the `user_ebay_account` value. Along with, the included "reviewed conversation history:" header.

Vital as this process is what allows the local ai model to understand who is the sender of each of the messages. As otherwise the context the conversation provides would be completely lost.

It was also manually checked that once the initial reply had been generated by the ai model, the current reply copied by the user into the reply box, and the previous ai assistance conversation, as well as any new additional instruction to the ai entered within the `user_instruction_window` were all included within the collective prompt.

This was verified by printing its contents to the terminal, after submitting multiple instructions to the ai model.

One major bug discovered early on in development, of this prompt building functionality, was the original use of `return f.read` when loading the `business_info.txt` file. This was an unfortunate mistake as it caused my `build_prompt` method to end immediately after reading the file.

This error was not caught until the generated replies were tested. As before hand, the replies returned from the ai model were lacking in any form of context of the customer/business conversation, and was unable to follow any of the instructions given by the user. Resulting in replies that were largely unusable.

Originally, it was considered that this was due to the conversation being too heavily sanitised, before it was fed into the model. However, on review, after further testing it was found that neither the reviewed sanitised conversation, nor the users instructions had been included in the combined prompt sent to ollama.

After printing and inspecting the prompt itself, the `return f.read` was altered to `business_info = f.read` allowing the rest of the prompt to be combined.

Ensuring that the combined prompt of this workflow contained both the business information from `business_info.txt` as well as the full instructions imported from the `prompt_workflow_two.py` file. #### Workflow one response testing

The instructions imported from `prompt_workflow_one.py` when combined with the context supplied through the rest of the information within the final prompt, directly affect the reply generated by llama.

The wording and format of the instructions passed to the model matter immensely, as they specify exactly how to construct a reply suitable for ebay.

For example, the instructions currently given to my local model within the program require the text reply generated to be written english and to maintain a polite and professional tone throughout. In addition, the model is instructed to directly address the customers most recent un resolved message, after reading the conversation in the order it was received. Leaving earlier messages to stand as context, rather than allowing the model to respond to enquiries that have already been resolved.

Further instructions direct the model to produce replies in line with what is expected for the example ebay based business used within this project. During testing, undirected model behaviour often caused replies that did not fit the intended tone and style of what was wanted.

An example of this unwanted model behaviour, could be seen within the produced replies that would promote products unrelated to the conversation. The model would also produce overly formal, almost letter like formatting, or create replies that were disproportionately long in comparison to the customers original replies through the conversation.

Each of these problematic behaviours could only be addressed by adding direct instructions to the mode that described the desired alternative behaviour.

After each change, the resulting replies were again tested until consistent replies, that fit my expectations, were being produced.

Also, through testing, it was also noted that sometimes the model would be confused by leftover over sanitisation placeholders. This was also addressed within the instructions to ensure if the user accidentally did not replace these placeholders within the review dialog, the model would automatically ignore them from the context/final customer reply.

Reply quality as a whole, was tested using the business and product information, imported from the `business_info.txt` file, alongside the added sanitised conversational history between the user and the business. This was done to confirm that the model could use the supplied context when constructing its replies. And that the resulting responses produced were suitable for the conversation at hand, as well as being consistent with the supplied facts from the business information.

Lastly, although this process resulted with me producing a style of reply that was suitable for my own example business. The preferred response style, for any business that were to use this program, would naturally differ. As if the application was to be developed for commercial use in the future, each business would be required to provide its own instructions, and business information to meet the desired tone, wording, length and format of the replies they wanted the model to produce.

#### Workflow two response testing

The responses produced by my second workflow were also tested, as designed separately, this workflow offers general assistance to the user without the need to pass any customer/business conversations to the model.

To test the responses, the model was asked a range of questions on the content within the supplied `business_info.txt` file. The replies produced were then checked against this information to confirm that the model could produce accurate answers consistent with the business details when instructed by the user. General questions, including request for advice about ebays delivery system, were also asked to see if the model could reply to questions not on the topic of the related business. These responses were again checked manually.

Lastly, multiple questions were also submitted to the model within the same conversation to confirm after each question and response, both the users question and the corresponding generated response were stored within the `text_conversation` list. As this stored history is returned and included within each subsequent prompt within the session. Allowing the model to understand the ongoing back and forth exchange, to maintain context, throughout the conversation.

#### Ollama error handling

Failure handling for requests sent to the model was relatively straightforward to test. As by stopping the locally running model before attempting to generate a response, the http request would then fail, raising an exception within the `call_ai` method. 

This method is present within both workflows files that communicate with the local mode, and this exception, once caught, would trigger a warning message to be displayed to the user. Through this message, the user is instructed to check on the local ollama model, to ensure it is currently running. As when no generated text is returned, the generation process is halted automatically, and the `call_ai` method returns a `none` value. Allowing the user to re attempt the generation process once again, after acknowledging the warring dialog.

Both of the workflows files within my program also include a sixty second timeout for the http requests made to the ollama model.

The intention of these timeouts is to prevent an indefinite wait in the event that the model accepts the connection, but fails to produce a response for my application. However, triggering this scenario for the purpose of testing, proved difficult. As stopping the model entirely would cause an immediate connection failure, rather than the delayed response that would trigger the timeout. Consequently this timeout functionality could not be directly tested.

## User interface testing

### Login process

The entire login user interface was tested to ensure that the correct warning dialogs were displayed to the user, when attempting to create an account using empty username and password fields.

Password confirmation was also tested by inputting differing passwords within the password and confirmation fields of the account creation dialog. In an effort to verify if the user would be correctly notified of the mismatch, and that the account itself would not be written to the database as a result.

Also checked, was the ordering of the dialogs within the pyside6 object tree. This was done by following the sequence of dialogs from the initial window through to the main chat widget window. Ensuring that windows themselves opened and closed correctly, leaving no windows orphaned behind.

This was key, as one bug identified during this process was the misplacement of `auth_dialog.exec` within `login_dialog.py` which was missplayed outside the conditional block responsible for creating the `auth_dialog` itself.

This file is effectively responsible for starting the oauth process from within the user interface. And if a valid token already existed within the applications file, the conditional block would be passed over, the auth dialog would never be defined or executed.

Because `auth_dialog.exec` was outside the conditional block, when reached and executed by the program, as it was not accompanied by the lines of code that initialized the dialog, the program would effectively crash.

The fix was simply to move `auth_dialog.exec` back into the conditional. When testing it was found that, now when a valid token existed the login process would continue as normal. And if the token data was missing or expired, a new authorisation attempt would be initiated.

### Conversation display

The conversation list within `chat_widget.py` was also tested manually, by observing whether all of the conversations active within the connected ebay messaging account were being correctly displayed within my application. 

Each conversation within the list was also checked to confirm that the corresponding message thread was loaded, and displayed for the user within `message_window`. It was also verified that by selecting a new conversation, `message_window` would be cleared before displaying the newly selected conversation. This is addressed in more detail below.

The alignment of the messages within the conversation display, which is itself a `qtextedit` widget, was also checked to confirm that message alignment was correct. With customer messages displayed to the left hand side, and the sellers messages are displayed on the right.

Originally the conversation’s display was extremely visually confusing. So during testing it was decided that a comparison between the `sender_username` field of each message object, and the currently selected customer’s username stored within `self.selected_customer`, would be used to separate the messages, improving the readability of the information.

### Reference id/item list compromise

The item names displayed as the topic of the conversation within the `chat_widget.py` list. Are manually assigned to the reference number of each conversation, done so through a python dictionary, imported from the `item_ref_dict.py` file. This is how my program is able to display this information, as if a conversation reference id matches one of the keys within this dictionary, the associated item can be accessed through the value.

This is how my program understands what items are related to each conversation, to show in the display. 

However, in the future, it is planned that another api call will be made to a separate api, to pass each conversations reference id to ebay to receive the related items name. But at this point, with how complex this program already is, the plan is to manually assign the names until everything else within the application is working as intended.

### Conversation selection

Selecting a conversation from the list, again within the `chat_widget.py` file, confirmed that the `qlist` widget items all contained the correct conversational ids. 

The id values assigned to each of the list items are done so through qt user role system. Allowing my program to cleanly retrieve the id on selection, via `list_item.data(qt.userrole)` without relying on the visible text of the item.

Each time an item is selected the id value is then passed to `get_conversation_messages` correctly, to be used to create the requests necessary to allow my application access to the conversational data through ebays api.

Once received, the thread belonging to the selected conversation is then processed and displayed within the window.

One issue however, identified through the task of conversation selection, was that when a new conversation was selected, the previous conversation messages would not be replaced within the window. This consequently caused the new conversation to be appended below the last. This was simply fixed though, by calling `self.message_qtextinput_window.clear` before the new conversations messages were rendered within the window.

Another bug discovered was that message data returned by ebay would be received by my application in the opposite order to what was expected. This meant that the newest messages in the conversion would appear at the top of the window.

To fix this all that was needed was the introduction of a new method in `reverse_messages` which rebuilt the list by inserting each message at the index of zero. Causing the oldest messages within the conversation to now appear at the top.

Lastly, storing the `conversation_id` directly within the list using the `qt.userrole` system was incredibly important as a design choice. As it was through testing, it was realized that it was possible for two conversations to be held with the same customer, just for two separate items.

With each conversation, holding their unique identifier of a `conversation_id` instead of relying on the visible customer username to select conversations, identifying a specific conversation even with the same customer was now a non issue.

### Faulty conversation exclusion

Through further testing of the conversation list it was found that some conversations, when selected, would return a `404` item not found response when the specific conversation id was sent to the messaging api endpoint.

This was later found to be as a result of previously deleted conversations that were still included within the accounts list of conversations, produced by ebay themselves.

As talked about within my `desing.md` file, the solution to this issue was to create both a temporary and permanent list of faulty conversation ids, that would be automatically excluded from the conversation list when built.

Further testing confirmed that the permanent conversation ids were compared to the ids sent by ebay, and that any matches would automatically be excluded from the list. Therefore, these conversations would not appear within the interface.

Runtime handling was also tested, by opening the unavailable conversations of the permanently excluded ids, that were temporarily included within the list. The resulting failure to obtain the message data caused the intended warning to be displayed and the `conversation_id` involved was added to the sessions exclusion set.

The conversation list was then rebuilt, confirming that the newly identified conversation ids, and their subsequent conversations, were removed from the interface. Preventing the user from reopening the same faulty conversation.

Note, that these ids within the sessions exclusion set, could be accessed inside the programs files in runtime. In the case where the user wanted to add these ids to the permanently excluded list.

### Qt stylesheet

The last file to be tested within my program, was the `qt_style_sheet.py` file. Containing the qt style sheets, not css, used to style many of the individual widgets throughout the desktop application.

Many of the variable names within my project had undergone slight changes through development. So many of the class selectors applied to widgets, message boxes, and button states, had to be corrected.
